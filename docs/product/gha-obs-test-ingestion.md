# 테스트 문서: 이벤트 수집

> 대상 PRD: [gha-obs-prd-ingestion.md](./gha-obs-prd-ingestion.md)

## 검증 대상 AC

- AC1-1: 조직 단위 이벤트 구독
- AC1-2: 서명 검증 및 수신·처리 분리
- AC1-3: delivery 단위 멱등 수신
- AC1-4: 누락 탐지
- AC1-5: Backfill 재수집
- AC1-6: 수집 상태 자체의 관측

## 공통 사전 조건

- 테스트용 조직과 최소 2개 레포, 각 1개 이상의 워크플로
- 페이로드 고정본(fixture): `workflow_run`(requested/in_progress/completed), `workflow_job`(queued/in_progress/completed with steps)
- 수신 엔드포인트에 임의 서명으로 요청을 보낼 수 있는 도구

## 테스트 시나리오

### 시나리오 1: 신규 레포 자동 커버리지

- **사전 조건**: 조직 webhook 설정 완료, 수집기 정상 동작
- **실행 단계**
  1. 조직에 새 레포 생성
  2. 워크플로 파일 추가 후 1회 실행
  3. 수집기에 별도 설정 추가 없이 대기
- **기대 결과**: 해당 레포의 `workflow_run` / `workflow_job` 이벤트가 수신되고, `workflow_job`의 `steps[]`에 step 정보가 포함되어 있다
- **검증 AC**: AC1-1

### 시나리오 2: 서명 검증

- **사전 조건**: 수신 엔드포인트 가동
- **실행 단계**
  1. 올바른 서명으로 요청 전송
  2. 서명 헤더를 변조하여 전송
  3. 서명 헤더 없이 전송
- **기대 결과**: 1번만 2xx + 저장, 2·3번은 401이며 원본 저장이 발생하지 않는다
- **검증 AC**: AC1-2

### 시나리오 3: 다운스트림 장애 시 수신 지속

- **사전 조건**: 수신기와 처리기가 분리 배포된 상태
- **실행 단계**
  1. 처리기를 강제 중단
  2. 이벤트 50건 전송
  3. 각 응답의 상태 코드와 소요 시간 측정
  4. 처리기 재기동 후 대기
- **기대 결과**: 50건 모두 2xx, 응답 시간 전량 10초 미만. 처리기 재기동 후 50건이 누락 없이 처리된다
- **검증 AC**: AC1-2

### 시나리오 4: 멱등 수신

- **사전 조건**: 초기화된 저장소
- **실행 단계**
  1. 동일 `X-GitHub-Delivery` + 동일 페이로드를 3회 전송
  2. 동일 delivery ID에 **다른** 페이로드를 1회 전송
- **기대 결과**: 1번 → 원본 레코드 1건, 응답은 3회 모두 2xx. 2번 → 추가 저장 없음, 다만 불일치가 경고 지표로 기록된다
- **검증 AC**: AC1-3

### 시나리오 5: 순서 뒤바뀜 수신

- **사전 조건**: 초기화된 저장소
- **실행 단계**
  1. `completed` 이벤트를 먼저 전송
  2. 같은 run의 `in_progress` 이벤트를 나중에 전송
- **기대 결과**: 두 이벤트 모두 Bronze에 원본으로 보존된다(수신 계층은 판단하지 않는다). 상태 수렴 판단은 Silver 계층의 책임 → 시나리오는 [Silver 테스트 문서](./gha-obs-test-silver.md) 시나리오 3으로 이어진다
- **검증 AC**: AC1-3

### 시나리오 6: 수집 중단 구간 누락 탐지

- **사전 조건**: 정상 수집 중
- **실행 단계**
  1. 수신기를 30분간 중단
  2. 중단 구간에 레포 2곳에서 워크플로 각 3회 실행 (총 6건)
  3. 수신기 재기동
  4. 누락 탐지 작업 실행
- **기대 결과**: 중단 구간의 6건이 backfill 후보로 탐지된다. 탐지 목록에 run 식별자와 소속 레포가 포함된다
- **검증 AC**: AC1-4

### 시나리오 7: 장시간 실행 run의 오탐 방지

- **사전 조건**: 터미널 미도달 임계값 6시간으로 설정
- **실행 단계**
  1. 7시간 이상 실행되는 워크플로를 시작 (또는 `in_progress` 상태로 7시간 전 타임스탬프의 이벤트 주입)
  2. 누락 탐지 작업 실행
  3. 이후 정상 `completed` 이벤트 수신
- **기대 결과**: 2번에서 backfill **후보**로만 분류되고 누락으로 확정되지 않는다. 3번 이후 후보 목록에서 자동 제거된다
- **검증 AC**: AC1-4

### 시나리오 8: Backfill 복구 정확성

- **사전 조건**: 시나리오 6 종료 직후 상태
- **실행 단계**
  1. 탐지된 6건에 대해 backfill 실행
  2. 복구된 데이터와, 동일 워크플로를 중단 없이 정상 수집한 대조군을 필드 단위 비교
- **기대 결과**: run/job/step 전 계층이 복구되고, 대조군과 실질 필드가 일치한다 (`source` 필드만 `backfill`로 차이)
- **검증 AC**: AC1-5

### 시나리오 9: Backfill과 webhook 동시 도착

- **사전 조건**: 정상 수집 중
- **실행 단계**
  1. 최근 24시간 구간에 대해 수동 backfill 실행 (이미 webhook으로 수집된 구간)
  2. Backfill 진행 중 새 워크플로 실행하여 실시간 이벤트 발생
- **기대 결과**: 중복 레코드가 생기지 않고, 실시간 수집이 backfill로 인해 지연되거나 유실되지 않는다
- **검증 AC**: AC1-3, AC1-5

### 시나리오 10: Rate limit 방어

- **사전 조건**: Rate limit 잔여량을 인위적으로 낮춘 상태(또는 임계값을 높게 설정)
- **실행 단계**
  1. 대규모 구간(예: 30일) backfill 실행
  2. 진행 중 rate limit 잔여량 추이 관찰
- **기대 결과**: 잔여량이 안전 임계 아래로 떨어지면 요청 속도를 낮추거나 일시 중단하며, 소진으로 인한 실패가 발생하지 않는다. 중단된 backfill은 재개 시 처리 완료 지점부터 이어진다
- **검증 AC**: AC1-5

### 시나리오 11: 자체 관측 지표 반응성

- **사전 조건**: 지표 수집 활성화
- **실행 단계**
  1. 정상 이벤트 100건 전송 → 수신 수 지표 확인
  2. 서명 오류 요청 10건 전송 → 검증 실패 지표 확인
  3. 처리기 중단 → 수신~저장 지연 지표 확인
  4. 시나리오 6·8 재현 → 누락 탐지/복구 지표 확인
- **기대 결과**: 각 단계에서 해당 지표가 기대 방향으로 변화하며, rate limit 잔여량이 상시 조회 가능하다
- **검증 AC**: AC1-6

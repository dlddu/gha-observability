# 테스트 문서: Bronze → Silver 정규화

> 대상 PRD: [gha-obs-prd-silver.md](./gha-obs-prd-silver.md)

## 검증 대상 AC

- AC3-1: 5계층 스키마 구현
- AC3-2: 중복 제거 및 상태 수렴
- AC3-3: 파생 지표 계산
- AC3-4: 비즈니스 일자 기준 재파티셔닝
- AC3-5: 멱등 재처리 및 전체 재구축
- AC3-6: 조직 전체 단일 질의

## 공통 사전 조건

- Bronze에 최소 2개 레포, 7일치 이벤트 적재
- 최소 1건의 재실행(rerun) 사례 포함
- 최소 1건의 실패 job과 실패 step 포함
- Bronze에 임의 이벤트를 주입할 수 있는 환경

## 테스트 시나리오

### 시나리오 1: 5계층 정합성

- **사전 조건**: 하루치 Silver 변환 완료
- **실행 단계**
  1. `dim_repo`, `dim_workflow`, `fact_run`, `fact_job`, `fact_step` 각각의 행 수 조회
  2. run별 job 수의 합계와 `fact_job` 전체 행 수 비교
  3. job별 step 수의 합계와 `fact_step` 전체 행 수 비교
  4. `fact_step`에서 `repo_id`만으로 필터링 (조인 없이)
- **기대 결과**: 2·3번의 합계가 일치한다. 4번이 조인 없이 동작하며 결과가 조인 방식과 동일하다
- **검증 AC**: AC3-1

### 시나리오 2: 재실행 구분

- **사전 조건**: 동일 `run_id`로 `run_attempt` 1(실패)과 2(성공)가 존재
- **실행 단계**
  1. 해당 `run_id`의 `fact_run` 행 조회
  2. 성공률 집계 쿼리 실행
- **기대 결과**: 행이 2건이며 `run_attempt`로 구분된다. `is_rerun`이 attempt 2에서 true다. 성공률 집계 시 두 시도가 각각 계산되어 결과가 왜곡되지 않는다
- **검증 AC**: AC3-1, AC3-3
- **비고**: run 계층 없이 job만 있었다면 두 시도의 job이 뒤섞여 구분 불가능했을 지점이다

### 시나리오 3: 순서 뒤바뀜 이벤트의 상태 수렴

- **사전 조건**: 초기화된 Silver
- **실행 단계**
  1. Bronze에 `completed`(conclusion=success) 이벤트 주입
  2. Silver 변환 실행 → 상태 확인
  3. 같은 run의 `in_progress` 이벤트를 **나중** 수신 시각으로 Bronze에 주입
  4. Silver 변환 재실행 → 상태 재확인
- **기대 결과**: 4번 이후에도 상태가 `completed`/`success`로 유지된다. 늦게 도착한 비터미널 이벤트가 확정 상태를 되돌리지 않는다
- **검증 AC**: AC3-2
- **비고**: 수신 시각 기준 단순 last-write-wins로 구현하면 이 시나리오에서 실패한다

### 시나리오 4: 중복 이벤트 제거

- **사전 조건**: 초기화된 Silver
- **실행 단계**
  1. 동일 run에 대한 완전 동일 이벤트를 Bronze에 3건 주입 (delivery ID는 상이 — backfill 상황 모사)
  2. Silver 변환 실행
- **기대 결과**: `fact_run` 결과 1건. 하위 `fact_job` / `fact_step`도 중복 없음
- **검증 AC**: AC3-2

### 시나리오 5: 파생 지표 정확성

- **사전 조건**: GitHub UI에서 소요 시간을 확인할 수 있는 실제 실행 1건
- **실행 단계**
  1. 해당 run의 `duration_sec`를 UI 표시값과 비교
  2. job의 `queue_wait_sec`를 `queued` → `in_progress` 이벤트의 페이로드 타임스탬프 차이로 수동 계산하여 비교
  3. step별 `duration_sec` 합계와 job `duration_sec` 비교
  4. `business_date`가 `run_started_at`의 UTC 일자와 일치하는지 확인
- **기대 결과**: 1·2번 오차 ±2초 이내. 3번은 step 합계가 job 시간 이하다(job에는 러너 준비 등 step 외 시간이 포함됨). 4번 일치
- **검증 AC**: AC3-3

### 시나리오 6: 큐 대기 시간의 기준 시각

- **사전 조건**: 수집 지연을 인위적으로 발생시킬 수 있는 환경
- **실행 단계**
  1. job의 `queued` 이벤트를 수신한 뒤, 수집기를 10분간 지연시킨 상태로 `in_progress` 이벤트 수신
  2. 해당 job의 `queue_wait_sec` 확인
- **기대 결과**: 수집 지연 10분이 대기 시간에 포함되지 **않는다**. 페이로드 타임스탬프 기준으로만 계산된다
- **검증 AC**: AC3-3
- **비고**: 수신 시각 기준으로 계산하면 파이프라인 지연이 러너 부족으로 오진된다

### 시나리오 7: 지각 데이터의 과거 파티션 갱신

- **사전 조건**: 3일 전 `business_date` 파티션의 집계값을 기록해 둔 상태
- **실행 단계**
  1. 3일 전 실행된 run을 backfill로 Bronze에 주입 (오늘 파티션에 적재됨)
  2. Silver 변환 실행
  3. 3일 전 `business_date` 파티션의 집계값 재확인
  4. 변환 중 해당 파티션에 대한 조회를 동시 실행
- **기대 결과**: 3일 전 파티션이 갱신되어 집계값이 증가한다. 4번의 동시 조회가 실패하거나 부분 상태를 반환하지 않는다
- **검증 AC**: AC3-4

### 시나리오 8: 멱등 재처리

- **사전 조건**: 특정 일자 Silver 파티션 존재
- **실행 단계**
  1. 해당 파티션의 행 수와 주요 컬럼 체크섬 기록
  2. 동일 Bronze 구간에 대해 변환을 3회 반복 실행
  3. 체크섬 재확인
- **기대 결과**: 3회 반복 후에도 행 수와 체크섬이 최초와 동일하다
- **검증 AC**: AC3-5

### 시나리오 9: 전체 재구축

- **사전 조건**: 7일치 Silver 존재, Bronze 보관 범위 내
- **실행 단계**
  1. 7일치 Silver 전 계층의 행 수와 체크섬 기록
  2. Silver 전체 삭제
  3. Bronze만으로 7일치 재구축
  4. 체크섬 대조
- **기대 결과**: 재구축 결과가 삭제 전과 완전히 일치한다
- **검증 AC**: AC3-5
- **비고**: 이 시나리오가 통과해야 스키마 변경·버그 수정 시 과거 데이터 소급 정정이 가능하다

### 시나리오 10: 조직 전체 단일 질의

- **사전 조건**: 최소 2개 레포, 7일치 Silver
- **실행 단계**
  1. 최근 7일간 실패율 상위 워크플로 N개 조회 (레포 미지정)
  2. 총 실행 시간 소비 상위 job N개 조회 (레포 미지정)
  3. 특정 step 이름의 전체 레포 실패 횟수 조회
  4. 각 결과를 레포별 개별 집계의 합과 대조
- **기대 결과**: 세 질의 모두 단일 쿼리로 결과를 반환하고, 레포별 합계와 일치한다
- **검증 AC**: AC3-6

### 시나리오 11: 데이터 없음과 수집 실패의 구분

- **사전 조건**: CI 실행이 실제로 없었던 일자와, 수집이 중단되었던 일자를 각각 준비
- **실행 단계**
  1. 두 일자에 대해 동일한 집계 쿼리 실행
  2. 결과 구분 가능 여부 확인
- **기대 결과**: 두 경우가 구분된다. 수집 중단 일자는 완결성 지표(PRD-1 / AC1-6)를 통해 "신뢰할 수 없는 구간"으로 식별 가능하다
- **검증 AC**: AC3-6
- **비고**: 구분되지 않으면 V1(가시성)이 아니라 잘못된 확신을 제공하게 된다

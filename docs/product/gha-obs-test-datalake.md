# 테스트 문서: 데이터레이크 적재 및 보관 정책

> 대상 PRD: [gha-obs-prd-datalake.md](./gha-obs-prd-datalake.md)

## 검증 대상 AC

- AC2-1: Bronze 원본 무손실 보존
- AC2-2: Hive 스타일 일 단위 파티션
- AC2-3: 파일 포맷 및 크기 규약
- AC2-4: 레이어별 TTL
- AC2-5: 파티션 프루닝 보장

## 공통 사전 조건

- 테스트 버킷과 Lifecycle 규칙 적용 권한
- 스캔 바이트 수를 측정할 수 있는 쿼리 환경
- 최소 3일치 이상의 이벤트가 적재된 상태

## 테스트 시나리오

### 시나리오 1: 원본 무손실 검증

- **사전 조건**: 특정 워크플로 실행 1건이 수집된 상태
- **실행 단계**
  1. Bronze에서 해당 `workflow_job` 레코드를 조회
  2. 저장된 원본 페이로드를 추출
  3. 동일 job을 GitHub REST API로 직접 조회
  4. 두 결과를 필드 단위로 비교 (특히 `steps[]` 배열의 각 원소)
- **기대 결과**: 페이로드의 모든 필드가 손실 없이 보존되어 있다. 수신 메타데이터(`delivery_id`, `event_type`, `action`, `received_at`, `source`)가 함께 기록되어 있다
- **검증 AC**: AC2-1

### 시나리오 2: 파티션 경로 정확성

- **사전 조건**: 수신 시각을 제어할 수 있는 환경
- **실행 단계**
  1. UTC 기준 자정 직전(23:58)에 이벤트 수신
  2. UTC 기준 자정 직후(00:02)에 이벤트 수신
  3. 각 객체가 저장된 경로 확인
- **기대 결과**: 두 이벤트가 각각 다른 일자 파티션에 저장되며, 경로가 `event_type=.../year=YYYY/month=MM/day=DD/` 형식이다. 로컬 시간대가 아닌 **UTC** 기준으로 분기된다
- **검증 AC**: AC2-2
- **비고**: 한국 시간(UTC+9) 기준으로 파티션이 잘리면 "어제 데이터"의 범위가 조회 도구마다 달라진다. UTC 고정을 반드시 확인한다

### 시나리오 3: Backfill 시 Bronze append-only 성질

- **사전 조건**: 3일 전 파티션이 존재하고, 그 객체 목록과 체크섬을 기록해 둔 상태
- **실행 단계**
  1. 3일 전 구간에 대해 backfill 실행
  2. 3일 전 파티션의 객체 목록·체크섬 재확인
  3. 오늘 파티션 확인
- **기대 결과**: **3일 전 파티션은 변경되지 않는다.** 복구된 데이터는 오늘 파티션에 `source=backfill`로 추가된다
- **검증 AC**: AC2-2

### 시나리오 4: 소파일 억제 및 병합

- **사전 조건**: 저트래픽 상태로 하루치 이벤트 적재 (파티션당 파일이 잘게 쪼개진 상태)
- **실행 단계**
  1. 병합 작업 실행 전 파티션의 파일 수·평균 크기 측정
  2. 일 1회 병합 작업 실행
  3. 병합 후 파일 수·평균 크기 재측정
  4. 병합 전후 레코드 수와 내용 대조
- **기대 결과**: 병합 후 1MB 미만 소파일이 파티션당 5개 이하로 감소하고, 레코드 수와 내용은 완전히 동일하다
- **검증 AC**: AC2-3

### 시나리오 5: TTL 적용 확인

- **사전 조건**: Lifecycle 규칙 적용 완료
- **실행 단계**
  1. `bronze/` 및 `silver/` 접두사의 Lifecycle 규칙 조회
  2. 보관 기간이 각각 90일 / 730일로 설정되어 있는지 확인
  3. (가속 검증) 보관 기간을 1일로 임시 설정한 별도 테스트 접두사에 객체를 넣고 만료 여부 확인
- **기대 결과**: 접두사별 규칙이 의도대로 적용되고, 기간 초과 객체가 실제로 만료된다
- **검증 AC**: AC2-4

### 시나리오 6: TTL 기준 시각 함정 검증 ⚠️

- **사전 조건**: `bronze/` TTL 90일 적용
- **실행 단계**
  1. 오늘 backfill로 **3개월 전 비즈니스 일자**의 데이터를 수집
  2. 저장된 객체의 경로와 생성 시각(LastModified)을 확인
  3. 해당 객체의 예상 만료 시점을 계산
- **기대 결과**: 객체 경로는 오늘 파티션(AC2-2에 따라)이고, 만료 시점은 **오늘 + 90일**이다. 경로상의 날짜와 무관하게 생성 시각 기준으로 만료된다는 사실이 문서와 일치한다
- **검증 AC**: AC2-4
- **비고**: 이 시나리오의 목적은 "고치는 것"이 아니라 **동작을 확인하고 문서화된 이해와 일치시키는 것**이다. 기대와 다르게 동작한다고 오해하면 보관 기간 산정 전체가 어긋난다

### 시나리오 7: 파티션 프루닝 효과

- **사전 조건**: 최소 30일치 데이터 적재
- **실행 단계**
  1. 날짜 조건 없이 전체 집계 쿼리 실행 → 스캔 바이트 수 기록
  2. 최근 1일 파티션만 지정한 동일 집계 쿼리 실행 → 스캔 바이트 수 기록
  3. 파티션 키를 문자열 함수로 가공한 조건(예: 경로 문자열 매칭)으로 동일 쿼리 실행 → 스캔 바이트 수 기록
- **기대 결과**: 2번의 스캔량이 1번의 약 1/30 수준으로 감소한다. 3번은 프루닝이 깨져 1번에 가까운 스캔량이 나올 수 있으며, 이 경우 해당 패턴을 금지 패턴으로 문서화한다
- **검증 AC**: AC2-5

### 시나리오 8: Bronze만으로 재구축 가능성 (경계 확인)

- **사전 조건**: Bronze TTL 90일 적용, 91일 이상 된 데이터가 존재하는 환경
- **실행 단계**
  1. 90일 이내 구간에 대해 Silver 재구축 시도
  2. 90일 초과 구간에 대해 Silver 재구축 시도
- **기대 결과**: 1번은 성공한다. 2번은 Bronze 원본이 없어 실패하며, **실패 사실이 명확한 오류로 보고된다**(조용히 빈 결과를 반환하지 않는다)
- **검증 AC**: AC2-1, AC2-4
- **비고**: 조용한 빈 결과는 "그 기간엔 CI 실행이 없었다"로 오독된다. 데이터 없음과 보관 만료는 반드시 구분되어야 한다

# PRD-1: 이벤트 수집 (Webhook 실시간 + Backfill 보정)

> 상위 문서: [gha-obs-values.md](./gha-obs-values.md)

## 달성 가치

- **V1: 조직 전체 CI 현황 가시성** — 조직 단위 구독으로 레포 등록 작업 없이 전체 커버리지를 확보한다
- **V2: 관측 데이터의 완결성** — 실시간 경로(webhook)의 구조적 취약점을 보정 경로(backfill)로 덮는다

## 배경 / 문제

Webhook은 **at-most-once에 가까운 전달**이다. 수신 서버 다운, 배포 중 재시작, 네트워크 단절, 처리 예외, GitHub 측 전달 실패 시 이벤트가 유실되며, 유실 사실 자체가 어디에도 남지 않는다.
반대로 REST API 폴링만 쓰면 지연이 크고 rate limit을 빠르게 소진한다.

→ **실시간은 webhook, 완결성은 backfill**이라는 이중 경로로 해결한다. Webhook은 빠르지만 못 믿고, API는 느리지만 정답이다.

## 범위

**포함**
- 조직 단위 webhook 수신 (`workflow_run`, `workflow_job`)
- 수신 이벤트의 원본 보존 및 멱등 처리
- 누락 탐지 및 backfill 재수집

**제외**
- 워크플로 실행 **로그 본문** 수집 (별도 PRD 대상, 용량 특성이 완전히 다름)
- Actions 청구/사용량 API 수집
- 알림·대시보드 (소비 계층은 별도 PRD)

## Acceptance Criteria

### AC1-1: 조직 단위 이벤트 구독

- **설명**: 조직 레벨 webhook 하나로 `workflow_run`, `workflow_job` 이벤트를 구독한다. 레포별 개별 등록을 하지 않으며, 조직에 새 레포가 생겨도 추가 설정 없이 수집 대상에 포함된다.
- **달성 가치**: V1
- **검증 방법**: 신규 레포를 생성하고 워크플로를 1회 실행 → 별도 설정 없이 해당 레포의 이벤트가 수신되는지 확인
- **비고**: `workflow_job` 이벤트의 `steps[]` 배열에 step 단위 정보가 포함되므로, step 수집을 위한 별도 API 호출이 필요 없다. 이것이 `workflow_job`을 반드시 구독해야 하는 이유다.

### AC1-2: 서명 검증 및 수신·처리 분리

- **설명**: 모든 요청은 `X-Hub-Signature-256` HMAC-SHA256 서명을 검증한 뒤에만 처리한다. 검증 통과 즉시 원본을 내구성 있는 저장소에 기록하고 2xx를 반환하며, 이후 가공은 비동기로 수행한다.
- **달성 가치**: V2
- **검증 방법**:
  - 서명 불일치 요청 → 401, 저장 없음
  - 정상 요청 → 응답 시간이 **10초 미만** (GitHub webhook 전달 타임아웃)
  - 다운스트림 처리기를 강제 중단시킨 상태에서도 수신 자체는 계속 2xx
- **설계 근거**: 응답 안에서 파싱·적재까지 처리하면, 다운스트림 장애가 곧 이벤트 영구 유실로 이어진다. 수신과 처리를 분리해야 장애가 "지연"으로만 남는다.

### AC1-3: delivery 단위 멱등 수신

- **설명**: `X-GitHub-Delivery` 헤더의 UUID를 멱등 키로 사용한다. 동일 delivery ID가 재수신되면(재전송, 수동 redeliver 포함) 중복 저장하지 않고 2xx를 반환한다.
- **달성 가치**: V2
- **검증 방법**: 동일 페이로드+동일 delivery ID를 3회 전송 → 저장된 원본 레코드 1건
- **비고**: 이 AC 덕분에 backfill이 webhook과 겹쳐도 안전하다. 멱등성이 없으면 재처리를 두려워하게 되고, 결국 누락을 방치하게 된다.

### AC1-4: 누락 탐지

- **설명**: 다음 두 방식으로 누락을 능동 탐지한다.
  1. **터미널 상태 미도달 탐지**: `queued`/`in_progress`만 관측되고 일정 시간(기본 6시간) 내 `completed` 이벤트가 오지 않은 run/job을 목록화
  2. **대사(reconciliation)**: 주기적으로 GitHub REST API의 run 목록과 수집분을 대조하여 차집합 산출
- **달성 가치**: V2
- **검증 방법**: 수신 서버를 30분간 정지 → 해당 구간에 실행된 run이 탐지 목록에 나타나는지 확인
- **비고**: run이 6시간 넘게 정상 실행 중일 수도 있으므로, 미도달 = 누락으로 단정하지 않고 **backfill 후보**로만 분류한다.

### AC1-5: Backfill 재수집

- **설명**: 탐지된 누락 후보에 대해 다음 우선순위로 복구한다.
  1. Webhook delivery 재전송 API (원본 페이로드 그대로 복구 가능, 가장 정확)
  2. REST API 직접 조회 — 실행 목록(`created` 범위 필터)과 실행별 job 목록
  - 임의 기간을 지정한 수동 backfill도 동일 경로로 실행할 수 있어야 한다
- **달성 가치**: V2
- **검증 방법**: 수신 정지 구간을 만든 뒤 backfill 실행 → 정지 구간의 run/job/step이 모두 복구되고, 정지 없이 수집한 경우와 동일한 결과가 되는지 대조
- **제약**:
  - Rate limit(설치 토큰 기준 시간당 5,000 요청, 조직 규모에 따라 상향)을 소진하지 않도록 남은 쿼터를 확인하며 조절한다
  - 페이지당 100건으로 조회하고, 대사 대상 레포를 최근 활동 순으로 제한한다
  - Webhook delivery 재전송은 GitHub의 delivery 보관 기간(약 30일) 내에서만 가능하므로, 그보다 오래된 구간은 REST API 경로만 쓴다

### AC1-6: 수집 상태 자체의 관측

- **설명**: 파이프라인 자신의 건강 상태를 지표로 노출한다. 최소한 다음을 포함한다.
  - 수신 이벤트 수 (이벤트 타입별)
  - 서명 검증 실패 수
  - 수신 → 원본 저장 지연 (p50/p99)
  - 누락 탐지 건수 / backfill 복구 건수
  - Rate limit 잔여량
- **달성 가치**: V1, V2
- **검증 방법**: 각 지표가 조회 가능하고, 인위적 장애(서명 오류 주입, 다운스트림 정지) 시 해당 지표가 반응하는지 확인
- **설계 근거**: "데이터가 안 들어오고 있다"를 사용자가 대시보드의 빈 그래프로 알아채는 상황을 막는다. 완결성(V2)은 측정되지 않으면 주장할 수 없다.

## 미결 사항

- 인증 방식: GitHub App vs 조직 PAT — App이 rate limit·권한 범위 면에서 유리하나 초기 설정 비용이 있다
- 누락 탐지 주기와 터미널 미도달 임계값(기본 6시간)의 실측 기반 조정
- 조직 내 레포 수가 많을 경우 대사 대상 선정 정책 (전수 vs 최근 활동 기준)

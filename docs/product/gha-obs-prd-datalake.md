# PRD-2: S3 데이터레이크 적재 및 보관 정책 (Bronze / TTL)

> 상위 문서: [gha-obs-values.md](./gha-obs-values.md)

## 달성 가치

- **V1: 조직 전체 CI 현황 가시성** — 모든 레포의 이벤트가 하나의 레이크에 모여 레포 경계 없는 질의가 가능해진다
- **V2: 관측 데이터의 완결성** — 원본 무손실 보존으로 언제든 재처리·재구축이 가능하다
- **V3: 질문 단위 분해 가능성** — 파티션 설계가 이후 계층 분해의 물리적 전제가 된다
- **V4: 예측 가능한 보관 비용** — 파티션 + TTL로 저장량과 스캔량의 상한을 고정한다

## 배경 / 문제

수집한 이벤트를 그대로 쌓기만 하면 두 가지가 동시에 무너진다. 첫째, 작은 JSON 객체 수십만 개가 흩어져 쿼리 시 전체 스캔이 발생한다. 둘째, 아무도 지우지 않아 비용이 무한 증가한다.

→ **Hive 스타일 일 단위 파티션**으로 스캔 범위를 자르고, **S3 Lifecycle TTL**로 보관 상한을 건다.

## 범위

**포함**
- Bronze 레이어 원본 적재 규약 (경로·포맷·파일 크기)
- 파티션 설계
- 레이어별 TTL 및 수명주기 정책

**제외**
- Bronze → Silver 변환 (PRD-3)
- 쿼리 엔진 선택 및 튜닝

```
s3://<bucket>/

    event_type=workflow_job/  year=2026/month=07/day=28/  part-*.jsonl.zst
  silver/                     (PRD-3에서 정의)
```

## Acceptance Criteria

### AC2-1: Bronze 원본 무손실 보존

- **설명**: Bronze에는 webhook 페이로드를 **가공 없이 원문 그대로** 저장한다. 여기에 수신 메타데이터를 함께 기록한다: `delivery_id`, `event_type`, `action`, `received_at`(UTC), `source`(`webhook` | `backfill`). 조직 내 모든 레포의 이벤트가 레포 구분 없이 **하나의 접두사 아래** 모인다.
- **달성 가치**: V1, V2
- **검증 방법**: 저장된 레코드에서 원본 페이로드를 추출해 GitHub API 응답과 필드 단위로 비교 → 손실 없음
- **설계 근거**: Bronze는 **재처리의 유일한 근거**다. 여기서 필드를 버리면, 나중에 필요해진 지표를 과거 데이터로 소급 계산할 방법이 영원히 사라진다. 스키마 변경 비용보다 원본 보존 비용이 싸다.

### AC2-2: Hive 스타일 일 단위 파티션

- **설명**: `event_type=<타입>/year=YYYY/month=MM/day=DD/` 구조로 저장한다. 파티션 값의 기준은 **수신 시각(`received_at`, UTC)**이다.
- **달성 가치**: V3, V4
- **검증 방법**: 특정 일자 파티션만 지정한 쿼리가 다른 일자 객체를 읽지 않는지 확인 (스캔 바이트 수 측정)
- **설계 근거 / 주의**:
  - Bronze 파티션 키를 **비즈니스 시각(run 시작일)이 아니라 수신 시각**으로 잡는 이유: 수신 시각 기준이면 Bronze는 **append-only**가 된다. Backfill로 3일 전 이벤트를 복구해도 오늘 파티션에 추가될 뿐, 과거 파티션을 다시 쓰지 않는다. 과거 파티션 재작성은 동시성 사고와 부분 갱신 실패의 주된 원인이다.
  - 대신 "7월 20일에 실행된 워크플로"를 Bronze에서 직접 조회하면 결과가 부정확할 수 있다. 이 불일치는 Silver에서 비즈니스 일자로 재파티셔닝하여 해소한다 (PRD-3 / AC3-4).

### AC2-3: 파일 포맷 및 크기 규약

- **설명**: 압축 JSONL로 적재하며, 파티션당 파일 수를 억제한다. 목표 파일 크기는 압축 후 **64MB~256MB**, 트래픽이 적어 목표에 못 미치는 파티션은 **하루 1회 병합(compaction)**을 수행한다.
- **달성 가치**: V4
- **검증 방법**: 임의 파티션 10개의 파일 수와 평균 크기 측정 → 1MB 미만 소파일이 파티션당 5개 이하
- **설계 근거**: 소파일 문제는 조용히 누적되다가 어느 날 쿼리 시간과 요청 비용을 동시에 터뜨린다. 이벤트 단위로 객체를 만들면 하루 수만 개의 객체가 생긴다.

### AC2-4: 레이어별 TTL

- **설명**: S3 Lifecycle 규칙으로 접두사별 보관 기간을 설정한다.

  | 레이어 | 기본 보관 | 근거 |
  |--------|----------|------|
  | `bronze/` | 90일 | 재처리 창구. 대부분의 재처리는 발생 후 수 주 내에 필요해진다 |
  | `silver/` | 730일 | 분기·연 단위 추세 분석(V1) 보장. 정규화 후라 용량이 훨씬 작다 |

  기간은 소유자 결정으로 조정 가능한 **기본값**이다.
- **달성 가치**: V4
- **검증 방법**: Lifecycle 규칙이 각 접두사에 적용되어 있고, 보관 기간을 초과한 객체가 실제로 만료되는지 확인
- **⚠️ 주의 — 반드시 설계에 반영할 것**: S3 Lifecycle의 만료 기준은 **객체 생성 시각**이지 파티션 경로의 날짜가 아니다. 오늘 backfill로 3개월 전 데이터를 새로 쓰면, 그 객체는 경로가 `year=2026/month=04/`여도 **오늘로부터 90일 뒤**에 만료된다. 파티션 경로 날짜대로 만료되길 기대하면 실제 보관 기간이 어긋난다.
- **함의**: Bronze TTL(90일)이 지나면 그 구간은 Silver 재구축이 불가능하다. Silver 스키마를 크게 바꿀 계획이 있다면 그 전에 Bronze TTL 연장을 검토해야 한다.

### AC2-5: 파티션 프루닝 보장

- **설명**: 날짜 조건이 있는 질의는 해당 파티션만 읽는다. 최근 1일 조회 시 스캔 대상이 1일치 파티션으로 제한되어야 한다.
- **달성 가치**: V3, V4
- **검증 방법**: 동일 결과를 내는 두 쿼리(날짜 조건 있음/없음)의 스캔 바이트 수를 비교 → 조건 있는 쪽이 파티션 비율만큼 감소
- **비고**: 파티션 키를 `WHERE` 절에서 문자열 함수로 가공하면 프루닝이 깨진다. 표준 조회 패턴을 문서화하여 이를 방지한다.

## 미결 사항

- Bronze 포맷: 압축 JSONL vs Parquet(raw payload를 문자열 컬럼으로) — 후자가 스캔 효율은 좋으나 원본 충실도 검증이 추가로 필요
- 버킷 분리 여부: bronze/silver를 접두사로 나눌지 버킷으로 나눌지 (권한 경계와 Lifecycle 관리 편의의 트레이드오프)
- 보관 기간 확정 (현재 90일 / 730일은 제안값)

# GHA Observability 제품 가치 문서

> 조직 전체 GitHub Actions 실행을 수집·저장·정규화하여, CI 현황을 한 곳에서 볼 수 있게 하는 관측 파이프라인.

## 제품 소유자

- **미지정** ⚠️ — 확정 필요. 모든 가치의 우선순위 판단 주체가 없으면 하위 문서의 트레이드오프(예: TTL 길이 vs 저장 비용)를 결정할 수 없다.

## 적용 범위

- 조직(Organization) 소속 **전체 레포지토리**
- 신규 생성 레포는 별도 작업 없이 자동 포함되어야 한다 (→ 조직 단위 webhook 전제)

---

## 제품 가치

### V1: 조직 전체 CI 현황 가시성

- **유형**: 추상적
- **설명**: 레포를 하나씩 열어보지 않고도 조직 전체의 CI 상태를 한 화면/한 쿼리로 파악할 수 있다. "지금 어디가 깨져 있나", "어떤 워크플로가 제일 느린가", "실패가 늘고 있나"를 레포 경계와 무관하게 답할 수 있는 상태를 뜻한다.
- **선정 근거**: 제품 소유자가 이 제품의 1차 목적으로 선택한 가치.

### V2: 관측 데이터의 완결성

- **유형**: 구체적
- **설명**: 화면에 보이는 숫자를 의심하지 않아도 되는 상태. 실시간 수집이 실패하더라도 누락이 **탐지**되고 **복구**된다.
- **측정 기준**:
  - 종료된 workflow run 중 silver 레이어에 터미널 상태로 수렴하지 않은 비율 < 0.1%
  - 누락 발생 시 24시간 이내 자동 복구
- **선정 근거**: 가시성(V1)의 전제 조건. 누락이 조용히 발생하는 대시보드는 없느니만 못하다.

### V3: 질문 단위로 분해 가능한 데이터

- **유형**: 구체적
- **설명**: 사용자가 궁금해하는 단위 그대로 데이터를 쪼개 볼 수 있다. 원본 이벤트를 매번 파싱하지 않고 **repo → workflow → run → job → step** 5계층으로 집계·필터링할 수 있어야 한다.
- **측정 기준**: 위 5계층 각각을 group-by 축으로 쓰는 질의가 추가 파싱 없이 가능
- **참고**: 요청 시 명시된 계층은 repo/workflow/job/step 4단계였으나, **run(실행 인스턴스) 계층이 빠지면 재실행(run_attempt)과 최초 실행을 구분할 수 없다.** 성공률·소요시간이 왜곡되므로 run을 별도 계층으로 추가했다.

### V4: 예측 가능한 보관 비용

- **유형**: 구체적
- **설명**: 데이터가 쌓여도 저장 비용과 쿼리 스캔량이 선형으로 폭증하지 않는다. 파티션과 TTL로 상한이 고정되어 있어 "언젠가 정리해야지"가 필요 없다.
- **측정 기준**:
  - 전체 저장량이 정상 상태(steady state)에서 상한에 수렴
  - 최근 1일 조회 시 스캔 대상이 해당 일자 파티션으로 제한

## 가치 간 우선순위

충돌 시 다음 순서로 판단한다.

1. **V2 (완결성)** — 틀린 데이터를 빠르게 보여주는 것보다 늦더라도 맞는 게 낫다
2. **V1 (가시성)** — 제품의 존재 이유
3. **V3 (분해 가능성)** — 가시성의 깊이를 결정
4. **V4 (비용)** — 위 셋을 훼손하지 않는 선에서 최적화

예: TTL을 짧게 잡아 비용(V4)을 줄이려다 분기 단위 추세 분석(V1)이 불가능해지면, V1이 우선한다.

---

## 이 문서의 사용법

이후 작성되는 모든 PRD·AC·테스트 문서는 "어떤 가치에 기여하는가"를 이 문서의 V1~V4로 명시해야 한다.
가치가 변경되면 하위 문서 전체의 정합성을 재검증한다.
